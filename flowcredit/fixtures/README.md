# fixtures — 已知缺陷靶子

审计引擎的 ground truth 在这里:每个靶子是一组**已确认、带证据指针**的缺陷,
规则引擎的最小验收标准是"能独立找出这些缺陷,且每条发现可一条命令重放"。

## demo-target/(演示靶子)

`demo-target/` 是一个**故意写坏的迷你 agent 应用(MiniAgent)**,作为审计器的
开箱范例:声明的缺陷 = 审批记忆按工具名键控(AGI-02)+ 明文密钥(AGI-03)。
30 秒体验:`python -m flowaudit.cli audit fixtures/demo-target`。
要点:**命中它的规则与审计 FCode 自己用的是同一套**(规则泛化),重放场景按
目标 profile 绑定(`scenario_by_profile`)——这就是"规则跨代码库,场景按靶子"的
活例子。

## fcode-self/

FCode 自身经 2026-10-30 全面评估确认的 7 个问题(`known-issues.json`)。
用自己当第一个靶子是刻意的:一个挖掘 agent 应用缺陷的工具,先把自己挖开。

**划分纪律**(2026-10-31 设计评审后确立):

- **dev 集**:FCODE-01/02/06 — 参与规则开发、提示词与示例
- **盲测集**:FCODE-04/07 — 不进规则、提示词与任何开发材料,专用于泛化检验
- **预留**:FCODE-03/05
- 另建无缺陷**负对照**与结构**变异**样本,防规则过拟合;检出率按根因统计,
  不按 PoC 数量

## synthetic/(Sprint 2)

人造漏洞靶,每个对应一条规则。生成原则:最小可复现,一个靶子只含一个缺陷,
让规则的判定契约可以精确对齐。

## 靶子纪律

- 靶子里的缺陷是**预置且声明的**——靶子文件头部注明缺陷位置与分类号,与
  Runtime 基准中"预置错误交付"同一纪律:失败保留在分母里,不藏。
- 靶子不是攻击武器库:PoC 以"证明缺陷存在"为限,不提供武器化增强。
